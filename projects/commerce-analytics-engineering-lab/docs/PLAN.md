## 1. 문제 정의 — 왜 이 문제가 실제로 존재하는가

쇼핑몰(커머스)에서 "오늘 매출이 얼마인가?"라는 질문은 간단해 보이지만, 실제로는 여러 시스템에 흩어진 데이터를 조합해야 답할 수 있습니다.

- **주문 시스템**은 주문이 들어왔다는 사실만 압니다.
- **결제 시스템**은 돈이 실제로 들어왔는지(성공/실패/취소)만 압니다.
- **환불 시스템**은 나중에 돈이 얼마나 돌아갔는지만 압니다.
- **재고 시스템**은 물건이 얼마나 남았는지만 압니다.

이 네 시스템 중 하나만 보고 매출을 계산하면 틀립니다. 예를 들어 주문은 들어왔지만 결제가 실패했다면 매출이 아니고, 결제는 됐지만 나중에 환불됐다면 그만큼 빼야 합니다. 더 어려운 점은 **환불이 이틀 늦게 시스템에 들어오는 경우**처럼, 데이터가 "늦게 도착"하면 이미 계산해서 리포트로 내보낸 과거 날짜의 매출까지 다시 고쳐야 한다는 것입니다.

이 문제를 방치하면 어떤 일이 생기는가:
- 같은 "오늘 매출"을 마케팅팀과 재무팀이 다르게 계산해서 회의 때마다 숫자 싸움이 납니다.
- 같은 주문 파일을 실수로 두 번 돌리면 매출이 2배로 부풀어 보이는 사고가 납니다.
- 늦게 들어온 환불을 반영하지 않으면, "이미 끝난 날짜"의 매출이 계속 틀린 채로 남습니다.

| 다음 개발자(미래의 나 포함) | 왜 이렇게 설계했는지 근거를 다시 찾아 헤매지 않도록 문서로 남김 |

## 3. 성공 기준 (이 설계가 맞았다고 판단하는 기준)

이 프로젝트는 아래 조건을 실제로 실행해서 증명하는 것을 목표로 합니다. 추측이 아니라 **실행 결과로 확인**합니다.

1. 같은 파이프라인을 두 번 돌려도 결과가 똑같아야 한다 (멱등성) → `scripts/verify_idempotency.py`로 SHA-256 해시 비교까지 실측
2. 환불이 이틀 늦게 들어와도 과거 날짜의 매출이 올바르게 다시 계산되어야 한다 → 합성 시나리오(`R102` 환불)로 재현
3. 잘못된 데이터(중복 ID, 음수 수량, 존재하지 않는 상품 참조)는 자동으로 걸러져야 한다 → 47개 데이터 테스트로 검증
4. 결과는 `PASS=71, WARN=0, ERROR=0, SKIP=0`처럼 숫자로 증명되어야 한다 (느낌이 아니라 실측)

## 4. 범위 (In-scope) / 범위 밖 (Out-of-scope)

**이번 버전에서 하는 것**
- 주문·주문상품·결제·환불·상품·고객·재고이벤트 7개 소스를 하나의 신뢰 가능한 매출/재고 지표로 통합
- 늦게 도착하는 데이터(late-arriving data)에 대한 재처리
- 로컬에서 재현 가능한 dbt + DuckDB 파이프라인

**이번 버전에서 의도적으로 뺀 것과 이유**
- **실시간 처리(스트리밍)**: 지금은 "정확한 배치 계산"이 먼저 증명되어야 할 단계라서, 실시간은 배치가 검증된 다음에 붙이는 게 순서상 맞다고 판단
- **클라우드 배포(BigQuery/AWS 등)**: 계정·비용·권한이 필요한 영역이라 로컬 재현성을 먼저 확실히 하는 것을 우선함
- **실제 고객 데이터**: 개인정보 처리 문제를 피하기 위해 결정론적 합성 데이터만 사용

## 5. 대안 비교 — 왜 이 설계를 선택했는가

| 검토한 대안 | 선택하지 않은 이유 |
| --- | --- |
| 순수 SQL 스크립트로 직접 계산 | 계층(staging/intermediate/marts)이 안 나뉘면 "매출 정의가 바뀔 때" 어디를 고쳐야 하는지 추적하기 어려움 → dbt로 레이어 분리 |
| 환불을 원래 것 안 고치고 "차감분만 새 행으로" 기록 | 과거 날짜 리포트를 다시 봤을 때 숫자가 안 맞아 보이는 문제가 생김 → 원래 날짜 자체를 재계산(restate)하는 방식 채택 |
| 멱등성을 "문서로만" 주장 | 말로만 하면 검증이 안 됨 → 실제로 두 번 실행해서 해시를 비교하는 스크립트로 증명 |

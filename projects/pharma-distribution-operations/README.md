# 의약품 유통 B2B 주문·출고·반품 분석

**2026-10-06 주간 실행 결과.** 공개 채용 공고에서 확인한 기술을 작은 합성 데이터 프로젝트로 재현했다. 실제 의약품, 약국, 환자, 처방, 고객 데이터는 사용하지 않았다. 실행된 범위는 CSV 생성, 입력 검증, SQLite 집계, 독립 재계산이다. BI 대시보드 화면이나 예측 모델을 구현했다고 주장하지 않는다.

| 직무 | 공고와 확인 상태 | 확인한 기술·업무 | 이 프로젝트에서의 역할 |

## 2. 먼저 답할 질문

> 주문한 물량 중 얼마가 출고됐고, 뒤늦게 입력된 반품까지 반영하면 운영상 출고금액은 얼마인가?

주문이 여러 품목을 담을 수 있으므로 `order_lines`는 **주문 품목 한 행**이다. 하나의 주문 품목은 여러 출고 행을, 한 출고 행은 여러 반품 행을 가질 수 있다. 출고와 반품을 먼저 주문 품목별로 집계한 뒤 결합해 다대다 조인의 금액 중복을 막는다.

| 파일 | 행 수 | 한 행의 뜻 | 핵심 연결 |
| --- | ---: | --- | --- |
| [`data/order_lines.csv`](data/order_lines.csv) | 77 | 주문의 한 합성 품목 | `order_line_id` 기본 키 |
| [`data/shipment_lines.csv`](data/shipment_lines.csv) | 64 | 한 품목의 한 번의 출고 | `order_line_id`로 주문 연결 |
| [`data/return_lines.csv`](data/return_lines.csv) | 16 | 한 출고의 한 번의 반품 | `shipment_line_id`로 출고 연결 |
| [`data/inventory_snapshots.csv`](data/inventory_snapshots.csv) | 8 | 시점·품목별 가상 재고 | 별도 관측값, 금액에서 역산하지 않음 |

처음 두 주문 품목은 손계산 예시다. `SYN-A` 10개×1,000원과 `SYN-B` 5개×2,000원을 주문하고, 각각 8개와 5개를 출고한다. B 1개의 반품은 9월 3일 발생하고 **9월 4일에 기록**된다. 따라서 주문금액 20,000원, 출고금액 18,000원, 기록 후 순출고금액 16,000원, 출고 충족률 13/15이다.

## 3. 순서대로 실행하는 방법

Python 표준 라이브러리만 사용한다. 다음 명령은 이 폴더에서 실행한다.

```powershell
python pipeline.py generate --output data
python pipeline.py analyze --input data --output analysis --as-of 2026-10-06T23:59:59
python audit.py --input data --analysis analysis
python -m unittest -v test_pipeline.py
```

1. **생성:** 고정 시드 `20261006`으로 합성 주문·출고·반품·재고 CSV를 만든다. 식별자는 `SYN-`, `ORD-`, `OL-`, `SH-`, `RT-` 형식의 가상 값이다.
2. **품질 검사:** 열·기본 키·참조 키, 양의 수량, 주문 전 출고 금지, 주문량 초과 출고 금지, 출고량 초과 반품 금지, 반품 발생일 ≤ 기록일을 확인한다. 위반 시 집계를 중단한다.
3. **분석:** 주문일과 제품의 코호트로 묶는다. `as-of` 시각 이전 출고만 포함하고, 반품은 물리적 발생일이 아니라 **기록일**이 `as-of` 이전인 건만 운영 대시보드에 반영한다.
4. **독립 감사:** [`audit.py`](audit.py)가 SQLite 집계 코드를 사용하지 않고 원본 CSV를 다시 합산한다. 일별·제품별 57행과 전체 합계가 일치해야 통과한다. [`analysis/audit.json`](analysis/audit.json)에 입력·출력 SHA-256을 남긴다.

## 4. 이번 실행에서 실제로 나온 값

기준 시각은 **2026-10-06 23:59:59**다. [`analysis/summary.json`](analysis/summary.json)과 [`analysis/daily_product_metrics.csv`](analysis/daily_product_metrics.csv)가 실행 결과다.

| 지표 | 값 | 계산 |
| --- | ---: | --- |
| 주문 수량 / 주문금액 | 618개 / 1,525,000원 | 주문 품목 수량×주문 당시 단가 |
| 출고 수량 / 출고금액 | 339개 / 880,000원 | 기준 시각까지의 출고 수량×같은 단가 |
| 기록된 반품 수량 / 금액 | 49개 / 135,000원 | 기준 시각까지 기록된 반품 수량×같은 단가 |
| 운영상 순출고금액 | 745,000원 | 출고금액 − 반품금액 |
| 출고 충족률 | 54.85% | 339 ÷ 618, 품목별 비율의 단순 평균이 아님 |

합성 데이터 안에서는 `SYN-B`의 출고 충족률이 67/157, 약 **42.68%**로 네 품목 중 가장 낮다. 따라서 시연용 대시보드라면 이 품목의 미출고 주문 90개를 먼저 살펴볼 수 있다. 이는 임의 규칙과 시드로 만든 **데모 결과**이며 실제 의약품 수급 문제를 뜻하지 않는다.

`inventory_snapshots`는 독립적으로 만든 가상 재고 관측값이다. 주문·출고·반품 수량과 재고 이동을 보존하는 모델을 아직 만들지 않았으므로 재고 부족의 원인 분석에는 사용하지 않는다. 단가·반품을 이용한 순출고금액도 세금, 할인, 배송비, 회계상 수익 인식이 빠진 **운영 지표**이며 회계상 순매출이 아니다.

## 5. 로컬 모델과 Codex 검수

초안 단계에서 GPU Ollama의 Qwen3.5 9B·Gemma4 12B·Phi-4 Mini가 각각 구조·설명·검수 후보를 반환했다. 그러나 주문 grain, 수량과 금액, 재고 계산에 오류가 있어 모델 출력 자체를 결과로 채택하지 않았다. Codex가 구조와 수식을 고쳐 실제 생성·집계·테스트·독립 감사를 실행했다.

NPU OpenVINO Qwen3 8B의 **별도 시험**에서는 공고 2건을 한 번에 입력했을 때 JSON 배열 형식이 깨졌다. 한 공고씩 짧게 재요청한 두 건은 빈 `<think>` 태그를 제거한 뒤 JSON으로 파싱됐고, 입력 요약의 직무·업종·기술과 2/2 일치했다. 표본 두 건은 자동화 도입 근거로 부족하므로 예약 작업의 NPU 단계를 아직 변경하지 않았다. 이 시험에서 NPU는 공고 태그 추출만 수행했고 집계 수치의 검수자는 아니다.

## 검증 범위

- `python -m unittest -v test_pipeline.py`: 5개 테스트 통과. 손계산·늦은 기록·다대다 중복 방지·잘못된 수량/날짜·고정 시드 재생성·결과 변조 탐지를 확인했다.
- `python audit.py --input data --analysis analysis`: 일별·제품별 57행과 전체 금액·수량이 독립 재계산과 일치했다.
- 산출물의 정확성은 **정의된 합성 규칙과 예제**에 한정된다. 공개 공고 원문 데이터나 실제 고객 정보로 학습·검증한 결과가 아니다.

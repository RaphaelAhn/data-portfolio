# Counie CS 운영 인텔리전스

> **개인 포트폴리오 프로젝트 · 2026.09–2026.09**  
> SQL 기반 운영 KPI 모니터링과 정책 근거형 AI 상담 지원 자동화 프로토타입

## 1. 한 줄 요약

가상 CS 티켓 데이터를 SQL·Python으로 구조화하고, SLA 위험과 문의 급증 후보를 탐지하며, 정책 근거·위험도에 따라 상담사 검수 큐를 구성하는 운영 지원 프로토타입을 구현하였음.

> 모든 티켓·상담사·정책·결과 수치는 결정론적으로 생성한 가상 데이터 기반이며, 실제 고객·상담사 성과·운영 효과를 의미하지 않음.

## 2. 문제 정의

CS 운영에서는 문의량만으로는 대응 우선순위를 정하기 어려움. 문의 유형·채널·시간대·재문의 여부·처리 상태를 함께 보지 않으면 SLA 위험과 고객 영향이 큰 티켓을 늦게 발견할 수 있음. 또한 LLM을 활용하더라도 정책 근거가 약하거나 금전·개인정보 관련 위험이 있는 문의를 자동으로 처리해서는 안 됨.

따라서 아래 세 가지 운영 질문에 답하도록 설계하였음.

1. 어떤 문의 유형과 시점에서 SLA·재문의 위험을 우선 점검해야 하는가?
2. 어떤 티켓은 AI 초안을 제시할 수 있고, 어떤 티켓은 전문 상담사 검수가 필요한가?
3. AI 지원의 품질·비용·지연시간을 어떤 CS KPI와 함께 측정해야 하는가?

## 3. 데이터·분석 설계

| 데이터 도메인 | 핵심 필드 | 분석 목적 |
| --- | --- | --- |
| 문의 티켓 | 생성 시각, 채널, 유형, 상태, 처리 시간, 재문의 여부 | 문의량·처리시간·SLA·재문의 KPI |
| 상담사 활동 | 상담사 ID, 스킬 그룹, 처리량 | 팀 단위 처리 여력 분석 설계 |
| AI 지원 로그 | 정책 버전, 검색 점수, 위험도, 라우팅, 검수 결과, 지연시간, 비용 | AI 품질·안전성·운영성 측정 |
| 정책 문서 | 정책 ID, 버전, 유효기간, 본문 | 답변 근거의 최신성 확인 |

`fact_ticket`, `fact_ai_assist`, `dim_agent`, `dim_policy_version` 중심의 데이터마트를 설계하였음. 티켓 ID 중복, 음수 처리시간을 검사하고, LLM 호출 전 이메일·전화번호 형태의 PII를 `[REDACTED]`로 마스킹하도록 구현하였음.

**근거:** [데이터 사전](data_dictionary.md), [PostgreSQL 데이터마트](../sql/cs_operations_datamart.sql), [파이프라인](../src/operations_pipeline.py)

## 4. SQL 기반 운영 KPI와 이상 징후 탐지

일별·문의 유형·채널 단위로 티켓 수, 완료 티켓 수, 평균 처리 시간, 재문의율, SLA 내 처리율을 정의하였음. 최근 7일의 티켓량 평균과 비교해 25% 이상 증가한 날을 조사 우선순위 후보로 표시하였음. 이는 원인을 확정하는 로직이 아니라, 운영 리더가 채널·유형·시간대를 추가로 점검할 시점을 제안하는 방식임.

결정론적 가상 데이터 실행 결과:

- 티켓 624건, 완료 티켓 601건을 분석하였음.
- 완료 티켓의 평균 처리 시간은 57.8분, 재문의율은 16.3%였음.
- 2026-08-19와 2026-08-20에 티켓량 급증 후보를 탐지하였음.

**근거:** `python data/generate_synthetic_data.py` 및 `python src/operations_pipeline.py` 실행 산출물 `outputs/operations_summary.json`

## 5. 정책 근거형 AI 상담 지원과 검수 라우팅

정책 문서의 유효기간과 버전을 기준으로 현재 티켓에 적용 가능한 문서를 검색하고, 검색 점수·재문의·미처리 상태·고위험 키워드를 조합해 라우팅하였음.

```text
티켓 유입
  → PII 마스킹·품질 검사
  → 문의 유형·긴급도 분류
  → 유효 정책 검색 및 근거 연결
  → 위험도 산정
      ├─ 일반 문의: 상담사 승인 후 답변 초안 활용
      └─ 재문의·SLA 위험·결제/보상/개인정보 위험: 전문 상담사 검수
```

가상 데이터 실행에서 159건을 전문 상담사 검수 큐로 라우팅하였음. 이 수치는 실제 자동화 성과가 아니라, 검수 기준이 적용된 오프라인 시뮬레이션 결과임.

현재 공개 구현은 재현성을 위해 규칙 기반 분류와 키워드 기반 정책 검색을 사용하였음. `llm_adapter.py`에는 OpenAI 호환 구조화 출력 연결 지점을 두었지만, 실 API 호출 결과는 포함하지 않음. 벡터 검색·reranking 기반 RAG 품질 비교는 **[근거 필요: 공개 가능한 평가 결과]** 상태임.

**근거:** [라우팅 정책](model_routing_policy.md), [LLM 어댑터](../src/llm_adapter.py), [골든셋](../evaluation/golden_questions.jsonl)

## 6. AI 품질을 CS KPI로 연결하는 측정 체계

| AI 품질 지표 | 함께 볼 CS 운영 지표 | 판단 목적 |
| --- | --- | --- |
| 정책 검색 정답률 | 상담사 답변 탐색 시간 | 근거 탐색 효율 확인 |
| 승인·수정·반려율 | AI 초안 사용률 | 상담 초안의 실용성 확인 |
| 답변 보류 적절성 | 고위험 검수 누락률 | 안전한 자동화 확인 |
| 응답 지연시간·추정 비용 | SLA 내 처리율·티켓당 비용 | 운영 가능성 확인 |

답변 정확도 하나로 자동화를 평가하지 않고, 상담사 검수 결과·고위험 문의 누락·SLA·비용을 함께 측정하도록 설계하였음.

## 7. 검증과 한계

- 이메일·전화번호 마스킹, 만료 정책 제외, 고위험 문의 전문 상담사 라우팅에 대한 단위 테스트 3건을 통과하였음.
- 실제 고객 데이터, 실제 상담 품질, 만족도, 운영 비용 절감, 프로덕션 배포 성과는 검증하거나 주장하지 않음.
- 실제 도입 전에는 정책 최신성, 개인정보 처리 근거, 접근 권한, LLM 응답 품질, 고객 만족도 및 AI 적용군/비적용군 비교가 필요함.

# 운영 및 데이터 품질 Runbook

## 품질 검사

| 검사 | 실패 신호 | 초기 대응 |
| --- | --- | --- |
| 이벤트 중복 | 동일 `event_id`가 둘 이상 존재 | 중복 원천과 재시도 로그를 확인하고 deduplication 상태를 점검 |
| 참조 무결성 | 주문이 없는 배차·완료 이벤트 발생 | 원천 토픽 지연 여부와 주문 이벤트 보존 기간을 확인 |
| 신선도 | 최신 `event_time` 또는 `ingested_at`이 기준보다 오래됨 | producer, Kafka consumer lag, Spark job 상태를 순서대로 확인 |
| 범위 오류 | ETA·배달 시간·상태 값이 계약 범위를 벗어남 | 배포된 producer 스키마와 최근 변경을 확인 |
| 마트 조정 | 주문 사실과 일별 마트 수치 불일치 | 영향 파티션을 재계산하고 변경 이벤트를 추적 |

## 지연 이벤트와 재처리

1. 수집 시각과 발생 시각의 차이를 기록합니다.
2. 지연 이벤트가 들어오면 해당 `order_id`를 다시 계산합니다.
3. 영향을 받는 주문일·지역·실험군 파티션을 다시 계산합니다.
4. 재처리 전후 row count, 중복 수, 핵심 지표 차이를 운영 로그에 남깁니다.
5. 재처리 결과가 기존 값과 달라졌다면 소비자에게 변경 시각과 영향 범위를 공지합니다.

## 관측성 설계

- 파이프라인: Airflow DAG 성공률·실행 시간·백필 실행 여부
- 스트리밍: Kafka consumer lag, 처리 지연, 레코드 처리량, 실패/재시도 수
- 데이터 품질: 중복률, orphan event 수, null 비율, 늦은 이벤트 비율
- 소비 계층: Trino/StarRocks 쿼리 실패율·지연시간·스캔량

## 장애 대응 원칙

- 대시보드 수치가 의심될 때 이전 정상 스냅샷으로 조용히 덮어쓰지 않습니다. 데이터 신선도와 품질 상태를 함께 노출합니다.
- 원천 오류와 변환 오류를 분리해 조사합니다.
- 원천 이벤트를 보존하고, 결정론적 변환을 유지해 재현 가능한 재처리를 가능하게 합니다.
- 재처리 대상은 전체 테이블이 아니라 영향을 받은 주문·파티션으로 좁힙니다. 단, 품질 규칙 자체가 바뀐 경우에는 전체 재계산 필요성을 별도 평가합니다.
